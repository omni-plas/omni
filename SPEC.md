# Omni — Universal Digital Creation, Transformation, Operations & Delivery System

## 1. Supreme Definition

Omni is an independent, self-contained, terminal-based programming language and an open-world universal digital system for defining, creating, transforming, compiling, building, testing, repairing, optimizing, packaging, installing, executing, deploying, maintaining, and extending digital entities and digital capabilities.

Its single fundamental capability is:

> **Given a digital idea, requirement, specification, operation, artifact, source, partial project, existing digital entity, or other sufficiently defined input at any meaningful stage of its lifecycle, Omni should be able to understand what is required, perform the remaining applicable work, and transform that input into the required usable digital capability or product.**

This applies to digital entities and digital operations of the past, present, and future, at any time and in any place, across relevant languages, platforms, operating systems, architectures, CPUs, runtimes, ABIs, formats, environments, and targets, provided that the information required to correctly model and realize the requested result is available or can be formally defined.

Omni is therefore not limited to a fixed language list, compiler list, operating-system list, target list, product category, era, file format, or catalog of operations.

Programming is one part of this larger lifecycle. Omni remains a real, independent programming language while the complete Omni system encompasses the broader path from idea, definition, source, or partial state to a usable result.

## 4. First-Capability Principle

A fundamental Omni objective is not merely to reproduce capabilities that already exist.

> **Whenever a digital capability is technically and formally definable and its required specifications, semantics, resources, and execution conditions can be satisfied, Omni should be capable of defining, constructing, and operationalizing that capability even if no previous system was capable of doing so. Omni may therefore become the first system to provide a particular digital capability.**

This principle applies to **every Omni capability**, not only to digital operations.

It applies to:

- New digital operations
- New digital entities
- New programming languages
- New compilers
- New runtimes
- New operating systems
- New architectures
- New targets
- New ABIs
- New file formats
- New protocols
- New libraries
- New packages
- New plugins
- New installation systems
- New deployment mechanisms
- New multimedia formats
- New classes of digital tools
- New systems that create other systems
- Any other formally definable digital capability

The principle does not imply magic or violation of physical or logical constraints. A genuinely new capability still requires sufficient specifications, semantics, resources, interfaces, and execution conditions.

## 14. Existing, Historical, and Future Operating Systems

### Existing Operating Systems

Omni must be architected to create, compile, package, deploy, and prepare installation artifacts for existing operating systems, subject to their specifications and capabilities.

Examples include Windows, Linux distributions, macOS, ChromeOS, Android, iOS, and other existing systems.

### Historical Operating Systems

Omni must support historical operating systems and their historical environments when the necessary technical information is available.

Obsolescence alone must not make a historical target outside Omni's model.

### Future Operating Systems

Omni must be able to model and target operating systems that do not yet exist when a sufficiently precise target specification is supplied.

Such a specification may define kernel interfaces, system calls, ABI, executable format, boot protocol, runtime model, filesystem model, device model, hardware architecture, security model, package model, installation protocol, and other target rules.

Omni does not magically predict an undefined future system. It provides a mechanism through which a sufficiently specified future system can become a target without fundamental redesign.

## 27. Product Completion Principle

When the user asks Omni to create a product, Omni should not stop at an intermediate artifact merely because that artifact is technically valid.

The system should continue through the applicable lifecycle until the requested level of completion is reached.

For example:

```text
Source Code → Executable
```

may be sufficient for one request, while:

```text
Source Code
 → Executable
 → Package
 → Installer
 → Installable Product
```

may be required for another.

For an operating system:

```text
OS Source
 → Kernel
 → System Components
 → Root Filesystem
 → System Image
 → Bootable Media
 → Installer
 → Installable OS
```

The requested product definition determines the required completion level.
